# Documentation Rules

Update documentation when behavior, setup, contracts, or operator workflow materially changes.

Documentation should describe the final behavior, not the implementation conversation.

Avoid:
- aspirational claims;
- claiming tests not run;
- stale screenshots;
- documenting abandoned approaches.

Useful docs include:
- configuration changes;
- new environment variables;
- new routes/contracts;
- operator-visible behavior;
- migration/runbook steps;
- verification limitations.

Comments belong where future maintainers need context that code alone cannot express.
